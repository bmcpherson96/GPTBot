# Architecture and implementation stages

Python 3.12 keeps image/perception/model work close to well-supported libraries. Qt Widgets via PySide6 Essentials provides a real Windows desktop UI without a browser runtime. SQLite avoids an external database. A separate Windows adapter confines capture, hooks, session checks and native input; the rest can be tested on Linux.

| Component | Source | Responsibility |
|---|---|---|
| Desktop UI | `teachdesk/ui.py`, `teachdesk/project_ui.py` | Library, review/questions, timeline, candidate editor, authorization, state overlay, worker lifecycle |
| Recording | `teachdesk/recording.py` | Explicit sessions, monotonic event/frame clock, 4fps frames, 20Hz motion samples, holds, privacy defaults, bounded queues |
| Desktop adapter | `teachdesk/windows.py` | Physical pixels, single-monitor/session/scope checks, HWND-bound Windows Graphics Capture (mss only enumerates monitor geometry), physical-only pynput hooks, SendInput, separate OS hotkey thread |
| Memory | `teachdesk/storage.py` | Transactional local task/demo/event/frame/version/run/audit storage, persistent answers, version promotion, deletion/invalidation |
| Perception | `teachdesk/perception.py` | Source-evidence cropping, contrast checks, translated template recognition, ambiguity rejection |
| Model/review | `teachdesk/model.py`, `teachdesk/model_schema.py` | Consent and configuration, selected evidence retrieval by task, answer reuse, real HTTP model request, untrusted JSON validation |
| Readiness | `teachdesk/workflow.py` | Graph contract and explicit evidence checklist; no confidence score |
| Execution/recovery | `teachdesk/execution.py` | Observe → branch/decide → gated visible input → visual verification; bounded graph traversal, correction pause, cancellation/release, outcome evidence |
| Controlled app | `teachdesk/lab.py` | Independent harmless application with movable controls, multiple observable states and an unexpected-state toggle |

The workflow is a graph, not an input-event replay. Nodes reference named visual targets cropped from included training frames. A node records its evidence and whether its rule is demonstrated or inferred. Graph metadata includes goal, named inputs, starting/completion predicates, supported scope, assumptions, exceptions and prioritized questions. Decisions are local graph decisions, not an online model chain. There are no shell/API action nodes. A new model response never writes source code or promotes itself.

Train/practice roles are established before capture. Practice evidence is not sent to the model. Versions are immutable documents; answers/review status are separate. Editing saves a new candidate. Promotion checks readiness in a transaction and retains prior versions. Intent edits, evidence exclusions/deletion and practice deletion invalidate relevant eligibility rather than fabricating a successful learning history. A crash marks in-progress sessions interrupted at the next launch. Qt's lock file prevents competing application instances for one store.

The runtime model is used only to construct candidates. Relevant examples are retrieved by task and role, then sampled at action-adjacent and time-spaced frames, with the selection disclosed. This is structured memory/context reuse, **not** fine-tuning or weight training. There is no vector database or cross-task semantic retrieval yet.

## Project-first interface (0.2.0)

`ProjectShell` supplies the home list, New/Open actions, three guided project steps, plain-language graph summary, beginning/end previews and Settings navigation. `MainWindow` remains the action controller; all recording, review, model, run and emergency actions route through its existing methods. The full workspace is retained in a scrollable Details page, so its minimum width no longer forces the main window off screen. No storage migration, readiness threshold slider or new capture backend is introduced. The simple review form saves real version answers/review status; branch destinations, loops, assumptions, completion conditions and inferred rules remain visible in its plan text.

Teaching and practice buttons explicitly assign their evidence roles. The normal practice picker omits incompatible evidence and uses dates, automatically choosing only when a single eligible example exists. Actual-action and consequential-step authorization remain mandatory. Normal mode uses the existing 120-second run bound; advanced mode retains its bounded duration control. The app never starts capture, AI learning or a run merely by opening a project. Current compatible teaching evidence can be learned without deleting older incompatible recordings: those are skipped before request construction, and old-source workflows still fail readiness/preflight.

## Strict response contract and local replay (0.2.1)

The observed 0.2.0 model failure occurred after JSON parsing, on input-name/description validation. The exact rejected JSON was not saved, so its precise bad field is unknown. To prevent this structural failure class, supported OpenAI endpoints default to `response_format.type=json_schema` with `strict=true`. Every object is closed and all its properties required; dynamic maps use arrays of named input/target records. Node variants carry only their supported fields, and key duration may explicitly be null to select the recorded-style default. Frame/demo enums come from the actual included training evidence. Local jsonschema validation, duplicate-ID checks, lossless map conversion, existing workflow validation and image materialization all run before acceptance. Syntax compliance cannot establish a correct task, crop or goal. Generic JSON mode remains configurable without automatic retries or fallback.

`model_replies` stores received text, selected source/frame IDs, prior-answer source provenance, sanitized usage counters, finish status, format mode and a SHA-256 fingerprint of the exact context/image bytes. It contains no request headers or provider HTTP error bodies. Active-key echoes in output are redacted and rejected. A reply is marked pending, rejected or accepted. Local recovery recomputes the context fingerprint, then reruns the same decoder/validators without an HTTP client; it cannot silently reuse an old goal, answer or excluded image. Accepted recovery saves an unreviewed workflow, not a verified run. Source deletion purges derived replies transactionally, including replies using prior answers from that source without its screenshots and project deletion cascades them. The simple Review page exposes recovery only when needed; raw reply text and deletion live under Details.

## Window image source (0.1.3)

The 0.1.1/0.1.2 scope guards proved insufficient on the user's Windows PC: a final desktop crop contained wallpaper/controller content before foreground-loss was reported. The source now uses Microsoft Windows Graphics Capture through the pinned `windows-capture` 2.0.1 Windows x64 ABI3 wheel, with `window_hwnd` set and no monitor/title-substring fallback. Each observation starts a one-frame native session, makes an owned RGB copy of the padded BGRA frame, and stops/joins the session in all result paths. It never leaves an idle capture source running. This deliberately trades per-frame setup overhead for bounded session ownership in the prototype. Sampling remains best effort. Foreground/visibility/session/display checks remain before and after acquisition.

Image dimensions must match `DWMWA_EXTENDED_FRAME_BOUNDS`, queried in physical pixels. This excludes the invisible resize margins of `GetWindowRect`; mismatches are rejected rather than rescaled. Cursor capture is disabled so cursor artwork does not contaminate visual templates. The OS capture border remains at its default; secondary-window inclusion also keeps the documented false default. Windows 10 2004+ is required for cursor-capture configuration. Protected or unsupported surfaces/drivers may fail or produce an unusable image; there is no screenshot fallback. Capture validation is now version 3, blocking all previous desktop-crop evidence before model transmission/readiness. No paid service is added.

## Stages

1. **Implemented vertical slice:** create task, local synchronized demonstrations, timeline, real configurable vision-model request and bounded graph contract, important-question answers and regeneration, visual execution adapter, emergency controls, persistence, movable-target lab. Core behavior is tested; the native Windows/model gates below remain open.
2. **Implemented expansion:** multiple training/held-out examples, exclusions and mistake intervals, task library/readiness, branch coverage and bounded loops, correction pauses, candidate isolation/promotion/rollback, performance history, local failure evidence, basic separately learned interaction timing/path profiles. Statistical style fidelity and real Windows performance remain unverified.
3. **Next gate:** run the native Windows checks and the real model-generated lab protocol. Collect actual frame alignment, stop latency, template robustness and model box/clarification failures. Fix demonstrated defects before supporting the user's game. This requires an interactive Windows machine and a configured vision endpoint; Linux/mock transport cannot establish these claims.
4. **Later product work:** reviewed accessible/semantic perception, robust text-variable predicates and cropping UI, representative task-specific retrieval beyond bounded prompts, explicit visual recovery/subworkflow authoring, stronger privacy/field exclusions, style evaluation against reserved trajectories, richer application authorization policies, packaging/signing and monitored deployment. No implementation of these is claimed.

## Official interfaces checked

At build time, direct documentation hosts were inaccessible from the cloud network. Official project documentation/source mirrors on GitHub and official PyPI distribution metadata were retrieved with TLS verification intact:

- [OpenAI official Python Chat Completions resource](https://github.com/openai/openai-python/blob/main/src/openai/resources/chat/completions/completions.py): messages, image content, JSON response mode and `max_completion_tokens`. The app uses HTTP via httpx, not an assumed SDK version or ChatGPT subscription.
- [Microsoft SendInput reference](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winuser/nf-winuser-sendinput.md): INPUT size, per-event return counts, held state and UIPI limits.
- [Microsoft RegisterHotKey reference](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winuser/nf-winuser-registerhotkey.md): thread message queue and MOD_NOREPEAT; F12 is reserved, so the app uses Ctrl+Alt+F8.
- [Microsoft SetThreadDpiAwarenessContext](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winuser/nf-winuser-setthreaddpiawarenesscontext.md), [GetWindowRect](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winuser/nf-winuser-getwindowrect.md), and [GetPhysicalCursorPos](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winuser/nf-winuser-getphysicalcursorpos.md): the 0.1.1 capture fix scopes DPI awareness on each calling thread and restores it; window-rectangle virtualization and invisible resize borders are accounted for in supported placement, and cursor positions use the physical API.
- [pynput official FAQ](https://github.com/moses-palmer/pynput/blob/master/docs/faq.rst): Windows event filtering. Returning false filters a listener callback, not the user's OS input; the app never suppresses physical input.
- [python-mss official project](https://github.com/BoboTiG/python-mss) and [Qt PySide6 metadata](https://pypi.org/project/PySide6/): distribution/API usage. `PySide6-Essentials` supplies the actual QtCore/QtGui/QtWidgets modules used.
- Current PyPI JSON release metadata for each pinned runtime dependency was checked. Windows x64 wheel availability is checked separately from running those wheels on Windows.

The 0.1.3 change additionally checked the following official references and pinned distribution source:

- [Microsoft CreateForWindow](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow.md): a capture item targets one HWND (Windows 10 1903+).
- [Microsoft DwmGetWindowAttribute](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/dwmapi/nf-dwmapi-dwmgetwindowattribute.md): HRESULT and physical extended-frame bounds; no DPI-scaled GetWindowRect mapping is used for images.
- [Microsoft IncludeSecondaryWindows](https://github.com/MicrosoftDocs/winrt-api/blob/docs/windows.graphics.capture/graphicscapturesession_includesecondarywindows.md): defaults to false.
- [windows-capture Python project](https://github.com/NiiightmareXD/windows-capture/tree/main/windows-capture-python) and [2.0.1 PyPI distribution](https://pypi.org/project/windows-capture/2.0.1/): inspected the actual wheel Python wrapper and release source for `window_hwnd`, BGRA row pitch, callback buffer ownership, stop/join behavior and optional-OS-setting constraints. The wrapper requires `opencv-python`, so that replaces the headless distribution on Windows. The Windows x64 ABI3 wheel and matching pinned OpenCV wheel are available. This inspection is not a native runtime result.

For 0.2.1, the official [OpenAI response-format SDK definition](https://github.com/openai/openai-python/blob/main/src/openai/types/shared_params/response_format_json_schema.py) and [Structured Outputs cookbook](https://github.com/openai/openai-cookbook/blob/main/examples/Structured_Outputs_Intro.ipynb) were checked for `json_schema`, `strict`, closed objects and required fields. The pinned jsonschema release and transitive dependencies were verified against official PyPI metadata; their Windows x64/Python 3.12 wheels downloaded successfully. This verifies the schema contract and artifacts, not an actual OpenAI acceptance result for this generated schema.
